# 保守性改善の方針

2026-11-03時点のAstra・Geminiによる独立レビューと相互確認、および利用者との合意に基づく。これは今回の修正作業の判断基準であり、実装手順書でも、変更済みの現行仕様でもない。実装した挙動は仕様書・関連文書へ反映する。

## 目的と優先順位

機能追加を重ねた再生セッションについて、利用者が成功と受け取った操作、保存された状態、再起動後の状態を一致させる。遅い外部処理が音声送信・状態確認を妨げる構造を減らし、失敗を追跡できるようにする。

優先順位は、停止・復元と保存の整合性、ロックとI/Oの分離、エラー処理・検証・開発運用の整理とする。大規模な作り直しや抽象化の追加自体を目的にしない。修正規模の小ささだけを理由に、整合性の問題を後回しにしない。

レビューは静的確認である。モデル間の合意も実行検証の代わりにはならない。指摘された経路を実装・仕様・テストで確認し、誤検知や仕様上の意図が判明した場合は修正対象から外す。

## 状態変更と永続化の原則

- 利用者が明示的に停止・スキップした曲は、管理再起動によって再開対象へ戻らない。手動曲と自動再生曲の双方に適用する。
- 管理再起動のための中断は、利用者による曲の終了と区別する。再生中は曲の先頭から再開し、停止状態は停止のまま復元する既存方針を維持する。
- チェックポイント保存が確定した後は、追加・消去・音量・自動再生設定・停止・スキップなどの変更操作を実行時点で拒否する。成功応答だけを返して変更を失うことは許容しない。読み取り操作は許可する。
- 保存失敗時には稼働中Botを維持する。追加・消去などで保存失敗を利用者へ知らせる保証を、非同期化の都合で失わない。
- 変更のない操作による不要な保存は減らす。ただし、未保存変更の再試行や保存先復旧後の再開を妨げない。
- 停止後処理中の追加拒否は今回は維持する。ロック改善を理由に、追加受付や再生開始の意味まで変更しない。

## 並行処理と責務の境界

ネットワーク接続・切断やファイル同期の遅延によって、音声送信・キャンセル・管理ステータス取得が同じロックで長時間待たされない構造を目指す。単にロックを外して新旧接続や保存順序の競合を生む変更は認めない。

接続・選曲・取得・保存の世代と完了条件を明確にし、古い処理の完了が新しい状態を上書きしないことを守る。管理ステータスは軽量に取得できることと、実際の再生状態に対応することの双方が必要である。

状態変更の入口と不変条件を集約する。複数のフラグには、goroutineの稼働と音声送信開始など異なる意味があるため、数を減らすことや単一enumへの置換を目的にしない。受付時と実行時の権限確認も、重複という理由だけで削除しない。

Discord非依存のキュー、自動再生の世代管理、取得・再生のテスト用差し替え境界、音声処理から独立したPresence管理は維持する。

## 合意した挙動

### 自動再生

最初の音声送信前に手動追加によって準備を中断した候補は、起点が変わっていなければ候補へ戻す。起点変更後の古い候補を戻さず、取得失敗や明示スキップでも戻さない。手動曲優先と、既に再生を開始した曲の扱いは維持する。

管理再起動による再開は同じ再生として扱い、履歴へ重複登録しない。利用者が同じ曲を改めて追加して再生した場合は別の再生と数える。履歴全体を単純に動画IDで一意化する変更は行わない。

候補取得の部分成功は引き続き採用する。失敗の記録を追加するために、利用可能な候補まで破棄しない。

### ニコニコ動画の再ログイン

通信障害・内部タイムアウトを認証拒否と区別する。一時的な障害だけで再起動までログインを停止せず、待機期間を置いて再試行可能にする。即時の反復試行は避ける。待機時間などの数値は、既存の認証世代管理・重複ログイン防止と整合する範囲で実装時に決定し、文書とテストに残す。

認証拒否時の扱い、親処理のキャンセル、初回ログインと再ログインの違いを混同しない。認証情報をログや利用者向けエラーへ露出させない。

## エラーと検証

利用者向けエラーは文言の完全一致ではなく、安定した分類で扱う。表示文言の調整がエラー分類を変えないようにする。Discord応答や取得の失敗は、操作名と安全な分類によって追跡可能にする。応答原文・認証情報・入力URLの無差別なログ出力は行わない。

通常の検証手順で本番構成のテストも実行されることを目指す。ビルド成功とテスト成功を区別し、通常チェックで確認できない範囲は明記する。並行処理の検証は時間任せではなく、処理順を制御できるテストを優先する。

DAVEのcallbacksとconnのキー不一致は、固定依存の実装では誤検知と確認された。現行不具合としてキー方式を変更しない。依存更新への備えとして実際の生成経路の契約を検証することは対象に含める。Guild IDだけに置換して接続世代の区別を失わない。

## Pure Go構成への一本化

Botの実行構成から旧libdaveバックエンドを廃止する。旧バックエンドの選択設定、起動・ビルド用タスク、専用の実行依存、ロールバック手順を残さない。既定のPure Go DAVEとgopus SIMDを本番構成とする。

名前にnativeが残っていても、現在のPure Go実装を削除しない。実態に合う命名へ整理する。FFmpegは現在の音声処理に必要なので維持する。race detector用のCコンパイラはBot本体のCGO依存とは区別する。

旧実装との比較・相互運用試験は通常開発の依存から分離する。歴史的な検証記録と結果は保存し、現行の起動経路として案内しない。比較実験の存続を理由に、通常のチェックやPure Goビルドへlibdaveの準備を要求しない。

## 開発運用と文書

古いバイナリ・ログの整理は、まず明示的に実行する管理タスクとする。通常起動時の自動削除は今回導入しない。稼働中・復旧用の世代と現在のログを保護し、キューや再生状態を削除対象にしない。保持数・期間は整理タスクの仕様として明示する。

アーキテクチャ文書は責務、状態遷移、ロック所有者、保存境界を追える構成へ整理する。機能の説明を無関係な節へ追記し続けない。CLI引数解析や開発タスクの重複整理では、再起動に必要な起動設定の引き継ぎを維持する。

Data APIのキャッシュと通信の直列化は、任意補完の失敗時フォールバックと重複取得抑制を維持したうえで改善する。キャッシュ命中の応答性を改善するために、API要求数や無料枠消費を不用意に増やさない。

## 完了の判断

ニコニコ認証：初回・再ログインの一時障害は1分の待機後に再試行可能とし、親キャンセルは待機を設定しない。通信障害・内部タイムアウト・親キャンセルについて、再試行抑制と復旧後の認証世代更新をテストする。認証拒否による停止と認証情報の秘匿は維持する。

自動再生候補の復帰：手動曲による準備中断では、取得世代とは別の起点世代を照合して候補を戻す。起点変更・スキップ・失敗・再生開始済みとの区別を再生ループの回帰テストで確認した。管理再開時の履歴は再生単位の識別情報をチェックポイントに保存して重複を防ぎ、再開前の再チェックポイントと同じ動画の新規追加を回帰テストで確認する。

追加の保存改善：空の追加要求・全件容量超過では正常な保存済み状態を書き直さず、保存失敗中は同じ操作でも再試行する。保存ファイルの更新有無と、保存先復旧後のキュー復元を回帰テストで確認する。

進捗：停止・スキップ済みの現在曲をチェックポイントで復元対象から除外する処理と、再生後処理より保存が先に到着する回帰テストを追加した。保存後のキュー消去・音量・自動再生設定・停止・スキップも実行時点で拒否する。通常の`mise run check`に本番構成（`davego,opus`・SIMD・CGO無効）のvetとテストを追加し、通常構成のテストと両構成のLinux/Windowsクロスビルドを含めて成功を確認した。他の改善項目は未対応。

合意した挙動がテストと現行文書で一致し、通常チェックが本番構成を検証でき、管理再起動後の状態復元を確認できたことを完了の基準とする。レビューの各指摘は、対応・誤検知・仕様決定・未対応を区別して追跡する。テスト実行なしに、静的レビューだけで競合解消と判定しない。

変更は関連する実装・テスト・文書を一つの作業単位にまとめてコミットする。Bot反映は既存の管理タスクを使い、曲境界での再起動、単一管理プロセス、ready状態を確認する。ユーザーから別途指示がない限りpushしない。
