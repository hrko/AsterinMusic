# ログ設計・ロガー改善の要件

## 目的と対象

本書は実装前の変更要件である。現在の挙動は[仕様書](specification.md)、構成は[アーキテクチャ](architecture.md)、操作は[開発・運用手順](development.md)を参照する。実装時に関連する現行文書を更新し、完了した検証と未確認の範囲を記録する。

通常のログから、どのBot・サーバーで何が起き、機能にどう影響し、最終的に何をしたかを追跡できるようにする。詳細な調査では、ログレベルを変更して判断過程を確認できることを目指す。ログの追加だけを目的に再生・復旧・保存の挙動を変更しない。

対象はBot本体の運用・診断ログ、依存ライブラリからのログ、およびその設定・開発環境での出力確認とする。利用者向けのDiscordメッセージ、再生履歴DB、将来の再生ログチャンネルは別機能として維持する。集中ログ基盤、分散トレーシング、メトリクス収集基盤、新しい非同期ログ基盤の導入は今回の必須要件に含めない。

## 記録する出来事とレベル

ログレベルは、エラー値の有無やリトライ回数だけでなく、その機能への影響とアプリが取る対応で決める。サーバー単位の機能停止もERRORの対象とし、プロセス全体の停止に限定しない。

| レベル | 判断基準 | 本Botでの例 |
| --- | --- | --- |
| DEBUG | 判断過程、個別試行、問題を示さない中断 | 接続通知の受信と採否、候補の除外理由、各再試行、明示スキップによるキャンセル |
| INFO | 運用上追跡する正常な出来事と重要な状態変化 | 起動・終了、状態復元、音声接続確立、移動・復旧の完了、明示停止 |
| WARN | 処理可能な異常、代替処理や部分成功による機能劣化 | 単曲取得失敗と次曲への移行、メタデータ補完の断念、一時的な接続障害 |
| ERROR | 機能継続・データ保持に重大な支障が生じた結果 | 復旧断念による再生停止、キュー・履歴の最終保存失敗、状態矛盾、起動不能 |

通常のVC移動や既定の無人退出は、それ自体をWARNにしない。利用者の入力誤りや権限不足は通常の拒否として扱い、個々の拒否をWARN／ERRORにしない。キャンセルは理由を区別し、停止・スキップ・旧世代の破棄はDEBUG、必要な処理の期限切れは影響に応じたレベルとする。

INFO以上では、起動・復元・終了、再生の開始と終了理由、接続・復旧の結果、保存失敗、利用する代替処理を追えること。再生開始は音声送信開始に対応させ、準備開始と混同しない。通常終了・スキップ・停止・取得失敗・接続失敗を区別する。繰り返す内部状態遷移や通知ごとの採否はDEBUGとし、正常運転で大量のログが発生しないようにする。

## イベント名と属性

自前の運用ログには、時刻、レベル、安定したイベント名、短い説明、対象を特定する属性を持たせる。イベント名は `voice.recovery.failed` のような分類とし、検索を説明文の完全一致に依存させない。以下の属性名を基本とし、該当するものだけを付ける。

| 対象 | 属性と意味 |
| --- | --- |
| 共通 | `event`、`component`。時刻・レベル・説明はHandlerの共通フィールドで出力 |
| 稼働単位 | `bot_id`、`guild_id`。起動時にはアプリのバージョンも記録 |
| 音声接続 | `channel_id`、`generation`、必要に応じて遷移前後の状態・切断コード |
| 再生・操作 | `playback_id`、`operation_id`。関連処理を結び付けるアプリ内の識別子 |
| 結果 | `reason`、`stage`、`action`、必要に応じて `duration_ms`、`attempt`、`queue_retained` |

IDは文字列、所要時間はミリ秒の数値、件数は整数、判定は真偽値で統一する。同じキーの重複や型の混在を避け、適用できない値は空文字・ゼロで埋めず省略する。関連付けには既存の再生単位などを再利用できるが、認証用セッションIDやトークンを使わない。トレース基盤がない状態で架空のtrace IDを導入しない。

異常の結果には原因分類と対応を併記する。例えば音声復旧の失敗では、どの段階で失敗し、曲をスキップしたのか、保持して停止したのかを区別できること。単に `upstream` とだけ記録せず、取得可能な安全なエラー分類・HTTPステータス・切断コードなどを補足する。

## 記録の責任とログ量

下位層は原因と失敗段階を呼び出し元へ返し、最終的な対応を判断する層が結果のログを記録する。同一の失敗を各層で同じ重大度のまま重複記録しない。再試行の詳細と、全体の復旧成功・断念は別の出来事として関連付ける。

同じ障害が続く場合は、最初の発生を記録し、同じ対象・理由の反復を集約する。抑制した件数と継続時間を要約し、復旧・最終失敗は残す。別のサーバーの障害をまとめて隠さず、集約用の状態にも上限と解放条件を設ける。具体的な間隔・件数は実装時に定数とテストで明示する。

20msごとのフレーム、Heartbeatごとの成功、音声・暗号化データ本体は常時記録しない。送信遅延などは曲単位の統計とし、通常の統計はDEBUG、品質劣化を示す場合は基準を定めてWARNにする。繰り返す結果の集約と、障害調査に必要な状態変化の記録を両立する。

## ロガーの所有とContext

`log/slog`を継続利用する。起動時に出力形式とレベルを設定した基本ロガーを作成し、App、再生セッション、接続管理、外部取得などへ `*slog.Logger` を明示的に渡す。基本ロガーの作成には `slog.New`、対象ごとの固定属性の追加には `Logger.With` を使う。関数ごとに独立したHandlerを作らない。

ロガーに固定する属性の寿命を、所有するオブジェクトに合わせる。Bot・サーバーIDはセッションに、VC ID・接続世代は接続試行に持たせる。長寿命のセッションロガーへ現在のVC IDを固定して、移動後も古い値を出す構成を避ける。並行する試行はそれぞれの派生ロガーを使い、共有ロガーの属性を可変状態として書き換えない。

処理の `context.Context` がある場所では `InfoContext` 等を使う。Contextへのロガー格納を基本方式にはせず、独自の取得APIは追加しない。ログのためだけにコマンドのContextを長時間の再生へ流用せず、キャンセルの寿命は従来の処理に従う。Contextを持たない起動・終了処理では通常の出力メソッドも使用できる。

自前の運用コードはパッケージ直下の `slog.Info` 等への依存を解消する。既定ロガーが必要なライブラリ向けの `slog.SetDefault` は起動時の互換処理に限定する。テストではロガーを注入し、グローバルロガーの差し替えに依存しない。

外部ライブラリには、ロガー注入APIがあれば共通設定を引き継いだロガーを渡し、コンポーネントを識別する。ライブラリ固有のメッセージを、自前の安定したイベント名と同じ契約にはしない。独自Handlerや包括的なLoggerインターフェースは、標準機能で満たせない要件が確認された場合に限って追加する。

## 秘匿と入力の扱い

全レベルで、Botトークン、Cookie、パスワード、APIキー、認証用セッションID、通信・DAVEの暗号鍵を記録しない。設定全体、HTTPヘッダー・応答本文、外部コマンドの引数や標準エラーを無条件に出力しない。DEBUGも例外にしない。

記録する属性は許可したものを選び、原文からの文字列置換だけに秘匿を依存させない。エラー原文を使う場合はその出所と内容を確認し、安全な分類へ変換できない外部エラーは原文を省略する。依存ライブラリのログも確認対象とし、安全性を確認できない詳細出力は全体のDEBUG設定で無条件に有効化しない。

通常ログには曲名、入力URL、ユーザー名、コマンドの自由入力を含めない。Bot・サーバー・VC・再生・操作の識別子は調査に必要な範囲で使い、追加者のIDは一律には記録しない。認証状態の比較には、値そのものの代わりに一致・変更の判定を使う。自由文字列は長さを制限し、改行・制御文字をエスケープして一件の入力が複数のログを偽装しないようにする。

## 設定・出力・保存

ログレベルはDEBUG／INFO／WARN／ERROR、形式はtext／jsonを設定ファイルで選択できるようにする。既定はINFO・textとし、既存設定に項目がなくても動作する。コンポーネント単位でレベルを上書きできることとし、音声接続の調査のために全ライブラリの詳細出力を有効化する必要をなくす。設定のキーと対応するコンポーネント一覧は実装時に設定仕様へ記載する。不正な値は起動時に拒否し、動的な設定変更は今回の対象外とする。

運用ログは標準エラーへ出力し、診断コマンドのJSONなど標準出力の結果と混在させない。text／jsonとも一イベントを一行に表現する。時刻はタイムゾーンが分かる形式とし、JSONは各行を独立して解析できること。初期設定の読取りに失敗した場合にも、安全な起動エラーを標準エラーへ出せること。

ログファイルの保存・ローテーションは開発管理タスクまたは配布先の実行環境が担当する。今回、Bot本体に独自のファイル管理を追加しない。既存の `.dev/logs`、`bot-logs`、`bot-cleanup` と稼働中ログの保護を維持する。保存先と閲覧権限は状態ファイルと同様に運用者が管理し、Git管理外とする。実行中のサイズ制限・自動ローテーションは別の運用改善とし、今回の変更で実装済みとは扱わない。

ログ出力の失敗を再生・保存処理の失敗へ変換しない。ログ出力自身の再帰的なエラーログ、無制限リトライ、無制限バッファを作らない。同期出力が待つ可能性を踏まえ、音声フレーム送信経路で出力せず、状態ロック内では必要な属性を取得し、可能な限り出力を外へ移す。通常のファイル出力で音声送信を悪化させないことを検証し、任意の出力先の停止に対する完全な非停止性は保証しない。

## 検証と完了条件

| 検証対象 | 確認する内容 |
| --- | --- |
| レベルと出力設定 | 既定値、不正設定、各レベルの除外、コンポーネント上書き、text／json、標準出力との分離 |
| 属性と寿命 | Bot・サーバーの分離、VC移動前後と接続世代、再生・操作の関連付け、必須属性と型の一貫性 |
| エラーと対応 | 通常キャンセル、タイムアウト、単曲失敗、復旧断念、保存失敗が適切なレベルと対応で記録される |
| 秘匿 | 合成したトークン・Cookie・APIキー・URL等を設定やエラーへ混ぜても、全レベル・全形式で漏れない。外部ライブラリの対象経路も確認 |
| ログ量 | 同一障害の反復、別対象の同時障害、復旧後の再発、集約状態の上限、要約と最終結果の保持 |
| 並行処理・出力障害 | ロガー注入テストと競合検査、失敗するWriterで再帰・panicを起こさないこと、通常出力時の再生継続 |

実装完了時は既存のチェックとWindows/Linuxビルドを通し、管理タスク経由のログ閲覧が継続できることを確認する。実Discordでの再生とVC往復移動について、INFOで結果、DEBUGで判断過程を追えることを確認する。実装したレベル・属性・設定を現行文書に反映し、未検証の経路は明記する。

## 実装状況

共通ロガーと設定読み込みの基盤を実装した。`logging.level`、`logging.format`、`logging.components`を検証し、未指定時はINFO・textとして扱う。コンポーネントはapp、voice、playback、source、history、state、interaction、updater、discord、daveを対象とする。

基盤のテストでは、コンポーネント別レベル、グループ属性の保持、依存ライブラリの原文・任意属性の除外、制御文字処理、並行出力、Writer失敗時に再帰しないことを確認した。CLIからAppへの注入、disgoへの制限付きロガー注入、起動・復元・更新確認・YouTube Data APIのログを移行した。API失敗経路では、合成したAPIキー・応答本文・曲名・URLを含めないことをtext／jsonで確認した。

反復障害の集約は、所有者ごとに最大256件、同じ対象・理由を1分間隔で要約する基盤を追加し、アクティビティ更新に適用した。復旧、上限による破棄、所有者終了時に抑制件数を残す。対象の分離、復旧後の再発、上限と解放、時間経過による要約はテスト済みである。

操作・履歴保存の失敗ログを注入ロガーへ移行し、通常キャンセルと保存失敗のレベルをテストした。接続通知はDEBUG、接続確立・復旧結果はINFO、接続断念はERRORに整理した。模擬接続によるVC往復で、ログのVC IDが移動に追随し、認証セッションID・トークンを含まないことを確認した。

キュー保存・DAVE・音声統計も注入ロガーへ移行した。キュー保存ではエラー原文を出さず、失敗と復旧を記録する。DAVEライブラリの原文は制限付きアダプターで除外する。音声統計は曲単位のDEBUGとし、20msを超える遅延が50フレーム以上、かつ全体の5%以上の場合をWARNとする。単発の接続待ちはこの基準ではWARNにならない。通常ビルドとdavego／opusビルドで関連テストを確認した。

再生開始を最初の送信成功に対応させ、再生試行ごとの`playback_id`で終了と音声統計を関連付けた。開始通知は試行ごとに1件だけ保持し、専用の観測処理が出力する。次の試行へ移る前に観測処理の終了を待ち、出力停止による無制限なgoroutine増加を防ぐ。履歴受付失敗の出力もフレーム経路から外した。送信失敗では開始を記録しないこと、開始が重複しないこと、Writerが停止しても後続フレームを送れることをテストした。

型付きエラーから認証・Cookie・通信・プロセス終了・保存権限などを分類し、HTTPステータス、Discordエラーコード、WebSocket切断コード、プロセス終了コードのみを補足する。取得段階の失敗を`stage=source`で識別し、パイプライン停止に伴う内部キャンセルで本来の取得原因が隠れないことをテストした。

コマンド・コンポーネント・モーダルの処理入口／終了をDEBUGで記録し、DiscordのInteraction IDを`operation_id`として関連付けた。イベントハンドラー内の応答失敗も同じIDを付ける。処理終了は成功を意味せず、入力拒否を含むハンドラーの終了を表す。複数操作の並行実行でIDが混在しないことをテストした。共通HandlerはGo標準の`testing/slogtest`にも適合し、予約キーとの重複を防ぐ。

応答編集ヘルパーまで操作IDを引き渡す。過去の履歴画面を編集する場合も、編集を起こした現在の操作IDを使う。HTTP 403を返す模擬応答で、テキスト・Embed・追送メッセージの失敗ログに同じIDとHTTPステータスが残り、操作トークン・本文・API応答原文を含まないことを確認した。

接続管理のロック内出力の削減、集約の適用範囲の拡大、全体検証と実Discord検証は未完了である。稼働中Botにはまだ反映していない。

## 公開資料との関係

以下は判断の参考資料であり、本Botのイベント名、レベルの具体例、設定方式は本書で定める。

- [Go：Structured Logging with slog](https://go.dev/blog/slog)、[slogのContexts](https://pkg.go.dev/log/slog#hdr-Contexts)：Handler・Withの利用、Contextがある場合の出力API。
- [Goの設計議論 #58243](https://github.com/golang/go/issues/58243)：Contextへのロガー格納は賛否があり標準APIから除外された。格納の一律禁止を意味しない。
- [OpenTelemetry Logs Data Model](https://opentelemetry.io/docs/specs/otel/logs/data-model/)、[例外ログの重大度](https://opentelemetry.io/docs/specs/semconv/exceptions/exceptions-logs/#severity)：重大度の意味、影響・文脈による判断、再試行と最終結果の区別。後者の重大度の節は調査時点でDevelopment扱い。
- [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)：調査に必要な属性、秘密情報の除外、入力処理、ログの保護。
- [Google SRE Workbook：Monitoring](https://sre.google/workbook/monitoring/)：原因調査用の記録と、集計による状態把握の役割分担。
- [The Twelve-Factor App：Logs](https://www.12factor.net/logs)：アプリの出力と実行環境の保存管理の分離。本BotではCLIの結果と分けるため運用ログを標準エラーに出す。
