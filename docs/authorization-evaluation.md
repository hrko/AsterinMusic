# Cedar Goの導入検証

## 初回評価

`github.com/cedar-policy/cedar-go v1.8.0`を固定し、`experiments/authorization/cedar_test.go`でBotから独立したテストを実施した。依存関係は`go.mod`と`go.sum`で管理する。本体への採用判断は、以下の未検証事項を確認した後に行う。

確認済みの結果：

- 許可なしは拒否、明示的拒否は許可より優先し、ポリシーの記述順に依存しない。
- 同じVCという条件、DJ属性による制限、個別の追加許可を表現できる。
- 拒否ルールの属性欠落は評価エラーとなるが、別の許可は成立する。アプリ側で診断エラーを検出して拒否する処理が必須。
- 実験的な厳格スキーマ検証で、未知の操作・属性、型違い、対象種別違いを検出できた。不正な構文はパーサーが拒否した。
- 変更しないPolicySetの32並行評価で結果が一致した。race detectorによる検証は未実施。
- CGO無効のWindowsテストとLinux向けテストバイナリのビルドが成功した。Linux上の実行は未確認。

スキーマ検証には`x/exp/schema/validate`を使用する。安定APIの`Policy.AST()`から実験的AST型への明示的変換が必要だった。この依存は本体導入時もCedarアダプター内に限定し、更新時に互換性テストを実行する。

## 評価時間

Windows amd64、Go 1.27.2、AMD RYZEN AI MAX+ 395で、同一の単純な条件を持つ全ルールが許可に一致する場合を測定した。

| ルール数 | 1評価あたり | 割当量 |
|---|---:|---:|
| 10 | 約1.1µs | 約2.2KB |
| 100 | 約6.5µs | 約16.6KB |
| 1,000 | 約70µs | 約123KB |

これは複雑な条件や巨大な属性集合の上限を保証する測定ではない。採用上限を決める前に、実際のプリセット、追加ルール、主体・ロール階層を用いて評価する。

## 再実行と残作業

mise環境で`go test ./experiments/authorization -bench . -benchtime=100ms`を実行する。このパッケージは通常の`mise run test`にも含まれる。

認可サービスを`internal/authorization`に実装し、[認可モデル](authorization-model.md)の両プリセット、複数ロール、管理者・所有者、本人追加曲、別サーバーのロール、追加拒否をテストした。広いpermitがあっても取得未完了・閲覧不可・サーバー不一致を拒否し、不正なforbidを注入した実行時テストでも安全側に拒否できた。共有サービスの並行評価、vet、Linux向けCGO無効ビルドも通過した。

ポリシー・属性の制限値と設定ファイル形式はモデルに記載した。ルール件数・個別サイズ・合計サイズ・ロール件数の上限ちょうどと超過をテストした。実サービスで250ロールを持つ主体を評価すると、追加ルールなしで約68µs・158KB、追加100ルールで約96µs・178KBだった。Entity構築とスキーマ検証を含む。この値は外部I/Oを含まず、複雑な式の最悪時間も保証しない。

設定読込テストでは、既定値、DJロール・追加ルールの読込、型・構文・スキーマ不正の拒否、エラーに本文を出さないことを確認した。Discord側の事実取得失敗、処理途中の権限変更、全入口への適用、実Discordでの確認はまだ残っている。認可サービスはBotへ接続していない。

## Discord事実取得アダプター

Bot初期化時にサービスを構築し、`authorizeTarget`にDiscord事実の取得・変換を実装した。まだコマンド・ボタンからは呼び出していない。各評価でRESTから利用者の所属ロールを取得し直し、Guilds Gatewayイベントで維持するサーバー・ロール・チャンネルの情報と組み合わせる。必須情報の欠落とREST失敗は拒否する。取得タイムアウトは1.5秒とし、セッションのロックを持ったまま呼ばない。

モックRESTを使い、DJロール削除後の再評価が拒否に変わること、取得失敗で許可しないことを確認した。これは実際の曲追加処理中の変更テストを代替しない。

チャンネル権限はeveryone、ロールの集約、メンバー個別の順に適用する。使用中のdisgo v0.19.6の補助関数はロールと個別の上書きをまとめて計算するため、ロール許可と個別拒否が競合する閲覧判定には使わない。専用の計算処理を作り、ロール間の競合、個別拒否・許可の優先、管理者、ロール欠落をテストした。根拠は[Discord公式の権限計算](https://docs.discord.com/developers/topics/permissions)。

参考：[Cedar Go公式リポジトリ](https://github.com/cedar-policy/cedar-go)。実験的機能の扱いは[導入方針](authorization-plan.md)に従う。
