# 再生履歴コマンドの要件

本書は、実装前に合意した`/history`の要件と技術選定をまとめる。履歴コマンド全体は実装中であり、以下の対応状況に記した範囲のみを実装済みとする。実装時には[現行仕様](specification.md)、[アーキテクチャ](architecture.md)、[設定](configuration.md)、[開発手順](development.md)へ対応する変更を反映する。

## 対応状況

利用者による実Discord確認で、履歴表示・ページ番号入力・再追加・PC／スマホの見た目に問題がないとの報告を得た。以下の表の実操作・表示の確認待ちは解消済み。追加改善として、不正なページ番号に対する再入力ボタンを実装し、モーダルの範囲表示と再入力後の元画面更新を`history_modal_test.go`で検証する。

SQLite保存層とsqlc生成を追加した。実DBで1万件のページ取得、VC境界、保持上限、重複登録防止、再オープン、将来版スキーマの拒否を検証するテストを用意している。再生開始・管理終了との接続、上限付き非同期保存、保持件数設定を追加した。DiscordコマンドとUIを追加し、画面の本人・サーバー・VC・メッセージ・操作世代・期限の一致、ページ操作、空表示、表示文字数のテストを追加した。再追加を含む実Discordでの操作・PC／スマホ表示確認は未完了。

画面の操作期限は作成から15分とし、最大1,024画面を保持する。期限後は再実行を案内する。ページ操作や曲の選択で期限を延長しない。新しい表示への更新ごとに操作世代を進め、古いボタンによる再操作を拒否する。

Windowsで`mise run check`（生成差分、vet、通常・本番タグのテスト、両OS向けCGO無効ビルド）を実行済み。Linuxでも本番タグのraceテストを実行し、実SQLiteの保持上限・再オープン・1万件ページ取得とDiscord処理のテストが通過した。DiscordのVoiceStateキャッシュを用いたテストで、VC移動・退出後の操作拒否と同一画面の処理中の連打拒否を確認している。実Discordでの操作・表示確認は、この自動テストとは別に行う。

LinuxではCGOを無効にした本番タグの`internal/history`・`internal/discordbot`テストも実行し、SQLite実行時にCGOを必要としないことを確認した。固定したsqlc 1.31.1のLinux版で`sqlc diff`が通過し、Windows版との生成差分はない。

| 要件群 | 確認根拠と残りの確認 |
| --- | --- |
| 記録時点・管理再開 | `history_record_test.go`で送信失敗は未記録、初回送信のみ記録、管理再開は同一日時・同一記録、新規追加は別記録を確認 |
| 保存・保持・ページ安定性 | `internal/history/store_test.go`で実DBのVC境界、保持上限、1万件の最終ページ、追加時の固定表示、削除時の失効、再オープン、将来スキーマ拒否を確認 |
| 音声処理との分離 | `internal/history/writer_test.go`で上限付き保存待ち、低速保存時のFlush期限、再試行回数、保存失敗通知、終了後の追加拒否を確認。Linux raceテストも通過 |
| UIの境界・構造 | `history_view_test.go`で本人・VC・メッセージ・世代・期限、移動・退出、連打拒否、ページ境界、空表示、Embed文字数を確認。PC／スマホでの実表示は確認待ち |
| 再追加 | `history_readd_test.go`で実保存層・取得処理・キュー挿入を通し、最新情報、本人による手動追加、通常／先頭の位置、付属リスト除去、取得中の移動・停止拒否、過去情報の保持を確認。Discord上での選択・再追加は確認待ち |
| 配布・開発環境 | Windows/Linuxビルド、Linux CGO無効での実DB、両OSのsqlc生成差分確認が通過 |
| 実Bot | 開発用設定で管理再起動し、`/history`登録成功、管理プロセス1つ・`ready=true`を確認。利用者によるページ番号入力を含む実操作の結果待ち |

## 目的と対象範囲

現在参加している音声チャンネル（VC）で再生した曲を振り返り、選んだ曲を同じVCのキューへ再追加できるようにする。履歴は再生開始の記録であり、最後まで聴いたことや再生完了を示すものではない。

今回の対象は閲覧、ページ移動、単曲の再追加、永続化である。複数Bot・複数VCでの同時再生は今回実装しないが、履歴の識別・保存境界は将来の対応を妨げない構造とする。

## 閲覧範囲と権限

| 項目 | 要件 |
| --- | --- |
| コマンド | `/history` |
| 対象 | 実行者が現在参加しているVC |
| 表示先 | 実行者本人だけに表示するEphemeralメッセージ |
| VC未参加 | 履歴を表示せず、VCへの参加を案内 |
| 他VCの履歴 | VC指定・サーバー全体表示は提供しない |
| 操作者 | 画面を開いた本人のみ |

ページ移動、ページ番号の入力確定、更新、曲の選択、再追加の各操作で、本人が元のサーバー・VCに引き続き参加しているかを確認する。退出・移動後は操作を拒否し、参加先での`/history`再実行を案内する。再追加は取得処理後の実行時にも通常追加と同じ権限・操作世代を確認し、取得中の退出・移動・停止などを見落とさない。

プライベートVCの履歴を、別VCへの参加やサーバー全体の閲覧によって取得できないことを守る。履歴IDを直接指定されても、元のサーバー・VC・表示対象との対応を検証する。

後からそのVCへ参加した人は、そのVCの過去の履歴も閲覧できる。参加時点以降に限定する仕様ではない。既に表示した内容を退出後に確実に消す保証はせず、退出後の新しい取得・操作を拒否する。

## 記録する再生

| 状況 | 記録の扱い |
| --- | --- |
| 最初の音声パケットの送信成功 | 履歴を1件記録 |
| 再生中 | 最新の履歴として閲覧対象に含む |
| 開始後のスキップ・停止・再生失敗 | 記録を残す |
| 開始前の取得・接続・音声送信失敗 | 記録しない |
| 管理再起動で同じ曲を再開 | 同じ再生として扱い、重複登録しない |
| 同じ曲を新しく追加して再生 | 別の再生として記録 |
| キューへ追加しただけ | 記録しない |

再生単位の識別は動画URLだけに依存させない。管理再開で再生開始日時を更新して最新位置へ移動させず、元の記録を維持する。履歴保存の再試行も同じ再生単位として扱う。

## 表示

画像なしのEmbedに、対象VC名と再生開始が新しい順の履歴を表示する。1ページは10曲とし、同時刻の記録にも一意な順序を設ける。曲の表記・短縮は[UI設計指針](ui-guidelines.md)と[キュー表示](queue-display.md)の共通ルールに揃える。

```text
再生履歴 · VC名

1. 曲名A
   5分前 · 4:15 · チャンネル名 · @追加者
2. 曲名B
   10分前 · 3:48 · チャンネル名 · 自動再生

[ ◀ 前へ ] [ 1 / 1,000 ] [ 次へ ▶ ] [ ↻ 更新 ]
[ 再追加する曲を選択 ▾ ]
[ キューに追加 ] [ 自分のキューの先頭に追加 ]
```

曲名は太字リンク、チャンネル名はリンク、追加者はユーザーメンションで表示し、通知は発生させない。自動追加曲は追加者の代わりに「自動再生」と表示する。再生開始時刻はDiscordの相対時刻を使い、長さ・チャンネル名・追加者とともに曲名直下のsubtext行へまとめる。狭い画面での折り返しは許容する。

履歴は記録時点の曲情報を表示する。表示のたびに外部サイトへ問い合わせない。欠けているメタデータは既存の曲表示ルールに従い、不明な長さを0秒などの確定値で示さない。

## ページ操作と表示の安定性

ページ操作は次の1行とし、ページ移動用のドロップダウンは設けない。

```text
[ ◀ 前へ ] [ 12 / 1,000 ] [ 次へ ▶ ] [ ↻ 更新 ]
```

| 操作 | 挙動 |
| --- | --- |
| 前へ・次へ | 1ページ移動。先頭・末尾では該当ボタンを無効化 |
| 中央のページ表示 | ページ番号を入力する画面を開く。入力確定時に範囲を検証 |
| 更新 | 最新の履歴を取得し、1ページ目へ戻る |

閲覧開始時点の履歴を基準にページ移動する。新しい再生が増えても、更新するまでページ内の曲や番号がずれないようにする。保持上限による削除で表示対象を維持できなくなった場合は、別の曲に黙って置き換えず更新を案内する。長時間のDBトランザクションを開き続けることは、この要件の前提にしない。

モーダルの入力欄には「ページ番号（1〜総ページ数）」を表示する。不正なページ番号では既存の履歴表示を維持し、本人専用のメッセージで「1〜総ページ数の整数を入力してください。」と［入力し直す］ボタンを表示する。ボタンから再入力モーダルを開き、正しい入力で元の履歴画面を更新する。再入力にも本人・VC・画面の操作世代・期限の検証を適用する。履歴が空の場合はその旨を表示し、移動・番号指定・再追加を無効化する。更新は利用可能とする。古い画面や無効な操作は、`/history`の再実行を案内する。

## 履歴からの再追加

表示中のページからドロップダウンで1曲を選択し、追加位置をボタンで指定する。同じ曲の履歴が複数ある場合は、番号などで区別できるようにする。選択前は追加ボタンを無効化する。

| 項目 | 要件 |
| --- | --- |
| 「キューに追加」 | `/play URL`と同じ通常追加 |
| 「自分のキューの先頭に追加」 | `/playnext URL`と同じ追加。他の利用者との順番は維持 |
| 追加先 | 履歴画面の対象VC。移動先VCへの転送はしない |
| 追加者 | 操作した利用者。元の追加者を引き継がない |
| 元が自動再生曲 | 手動追加として扱う |
| 取得対象 | 単曲のみ。元の付属プレイリスト・Mixは取り込まない |

再追加時に取得可否と最新のメタデータを確認する。削除・非公開などで取得できない場合は追加せず、本人に失敗を案内する。履歴自体の過去のメタデータは書き換えない。

通常追加のキュー上限・保存失敗・接続失敗の扱いを再利用する。例えば、追加成功後の接続失敗を「未追加」と表示して再試行による重複を招かないようにする。成功・失敗の結果は本人だけに表示し、履歴画面は残す。

処理中の連打による重複追加を防ぐ。成功後、ページ移動、更新時には選択を解除する。操作対象は表示番号やURLだけでなく、履歴IDで固定する。曲を再追加しても、音声送信が始まるまでは新しい履歴を作らない。

## 永続化と複数VCへの備え

履歴はSQLiteへ永続化し、再起動後も保持する。上限は既定でVCごとに10,000件とし、設定で変更可能にする。上限を超えた記録は、そのVCの古いものから整理する。他VCの再生頻度によって保持件数が減らないようにする。

| 保存情報 | 用途 |
| --- | --- |
| 履歴ID | 閲覧・再追加の対象識別 |
| サーバーID・VC ID | 閲覧、保存、保持件数の境界 |
| 再生セッションID | 独立した再生セッションの識別 |
| 再生単位ID | 管理再開・保存再試行の重複防止 |
| BotアカウントID | 担当Botの追跡。閲覧範囲の区切りには使わない |
| 再生開始日時 | 表示・並び順 |
| 曲のURL・タイトル・長さ・チャンネル情報 | 履歴表示と再追加 |
| 追加者・自動再生の区別 | 表示と記録の由来 |

音源・画像本体・認証情報は履歴DBへ保存しない。担当Botが変わっても、同じサーバー・VCの履歴を参照できる構造とする。複数VCの自動再生の重複回避用履歴は、それぞれの再生セッションで独立させる。

閲覧用履歴と既存の自動再生履歴は別に管理する。閲覧用の保持件数変更が選曲へ影響しないことを守りつつ、再生開始の判定と管理再開の同一性判定は共通化する。既存のキュー・再生状態の保存方式は今回変更しないが、重複防止に必要な再生単位の識別情報は管理再開をまたいで保持する。

## 保存処理と障害時の扱い

DB書き込みは音声送信とセッションのロックを長時間待たせない別処理で直列化する。履歴の保存失敗だけを理由に再生を停止せず、安全な診断ログを残す。閲覧に失敗した場合は空の履歴として扱わず、取得失敗を本人へ案内する。

非同期保存には、最初の送信成功からDB保存までの間隔がある。異常終了時に未保存分が失われ得ることを明示し、永続化済みの履歴と同じ保証をしない。通常の管理終了では保存待ちの処理を扱う方針を定め、管理再開時の重複防止と整合させる。保存要求の上限、再試行、終了待機の具体値は実装時に決め、無制限の滞留や再試行を避ける。

## SQLite・sqlcの採用方針

実行時は`modernc.org/sqlite`を`database/sql`経由で使用する。Bot本体のCGO非依存とWindows/Linux対応を維持する。`modernc.org/libc`は採用するドライバーが指定する版との整合を確認し、依存をまとめて固定・検証する。

SQLからGoの引数型・結果型・実行関数を生成するためにsqlcを採用する。SQLにはVC境界、ページ取得条件、重複防止、保持上限による削除を明示する。生成コードは履歴用パッケージ内に収め、権限確認・音声との連携・スキーマ移行はアプリ側で扱う。ORMは追加しない。

sqlcは開発用ツールとしてmiseでバージョンとロックを固定し、Windows/Linuxで利用できる構成にする。生成は`mise run sql-generate`にまとめ、SQLと生成Goコードを同じ変更でコミットする。生成コードを手編集せず、`mise run check`に`sqlc diff`による生成漏れ検出を組み込む。補助自動化が必要な場合はGoで実装する。Botの配布・起動時にsqlcを要求しない。

sqlcのSQLite対応は選定時の公式表でBetaである。必要なクエリを実際に生成・実行して採用版との適合を確認する。生成成功だけで権限条件・索引・ロック・スキーマ移行の正しさを保証しない。

参照した一次資料：

- [moderncの仕様とlibc依存](https://pkg.go.dev/modernc.org/sqlite)
- [sqlcのSQLite入門](https://docs.sqlc.dev/en/latest/tutorials/getting-started-sqlite.html)
- [sqlcの対応状況](https://docs.sqlc.dev/en/latest/reference/language-support.html)
- [sqlcの生成差分確認](https://docs.sqlc.dev/en/latest/howto/ci-cd.html)

## 実装時に確定する項目と検証条件

設定キー・上限の許容範囲、DBの配置・移行方法、画面の操作期限、非同期保存の再試行・終了待機、ライブラリーの固定バージョンは実装時に確定する。これらは本書で合意した閲覧境界・再生単位・保持件数・UIを変更する理由にはしない。

最低限、次の条件を検証する。

- 別サーバー・別VC・別ユーザーの履歴や操作が混ざらない。退出・移動後や取得中の移動でも再追加を拒否する。
- 最初の送信成功だけを記録し、管理再開・保存再試行では重複せず、同じ動画の新規追加は別記録になる。
- 10,000件で件数・ページ指定・最終ページを正しく扱い、閲覧中の追加や保持上限による削除で別曲を誤選択しない。
- 再追加が通常追加・先頭追加と同じ順番、追加者、容量・保存エラーの扱いになる。
- DBの低速化・保存失敗・閲覧との並行実行・管理終了でも、音声処理の長時間停止や保存の無制限滞留を起こさない。
- 永続化後の再オープン、スキーマ移行、VCごとの保持上限を検証する。
- sqlcの生成差分チェック、CGO無効でのWindows/Linuxビルド、両OSでの実DB操作を確認する。表示はPC・スマホで確認する。

## 今回の対象外

履歴検索、日付指定、利用者による履歴削除、履歴保存OFF、再生完了・中断理由の表示、他VCからの閲覧・再追加、専用チャンネルへの再生ログ投稿は含めない。実装開始前の過去の曲について、既存の自動再生履歴から完全な再生履歴を復元できるとは扱わない。
