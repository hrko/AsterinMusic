# 認可モデルと導入時の許可表

本書は導入用のモデルを定める。認可サービスと設定ファイルの読込・検証は実装済みだが、Discordの操作経路への接続は未実施であり、稼働中Botの権限はまだ変更していない。設定によるアクセス制御を運用開始するのは、全入口への適用と検証を完了してからとする。

## サービス境界

`internal/authorization.Service`はアプリ独自の主体・操作・対象・事実を受け取り、許可、安定した理由分類、関連ポリシーID、設定版を返す。評価不能時はエラーも返す。利用側は許可が明示された場合だけ実行する。Cedarの型はインターフェースに含まない。

主体はサーバーID、ユーザーID、同じサーバー内のロールID、管理者・所有者属性で構成する。対象はサーバー、Bot、再生セッション、VC、必要なら曲の追加者を持つ。CedarのUserとRoleのIDにはサーバーIDを含める。異なるサーバーの主体と対象の組み合わせは評価前に拒否する。

事実には、取得完了、対象を閲覧可能、対象VCに参加、いずれかのVCに参加、を区別して保持する。取得失敗を空のロール集合に置き換えず、取得完了をfalseとして拒否する。Cedar評価中に外部I/Oは行わない。

## 基礎プリセット

| 操作 | 共同操作 | DJ |
|---|---|---|
| ヘルプ、キュー・再生中・音量・自動再生状態の閲覧 | 閲覧可能な利用者 | 同左 |
| 履歴の閲覧 | 対象VCに参加 | 同左 |
| 曲追加、自分の次の番への追加 | 対象VCに参加 | 同左 |
| 履歴からの再追加 | 対象VCに参加。別途、履歴閲覧と追加先操作も許可が必要 | 同左 |
| 再開、停止、スキップ、全消去、音量変更、自動再生変更 | 対象VCに参加 | 対象VCに参加し、DJロール・管理者・所有者のいずれか |

既定は共同操作とする。DJ方式には1件以上のDJロール設定を要求し、未設定のまま一般利用者の操作を制限しない。管理者・所有者の許可も基礎ポリシーに含め、追加のforbidを優先する。本人の曲だけスキップ可能にする条件は追加permitで表現でき、DJの既定には含めない。

追加ポリシーで許可を広げても、Discordの閲覧制限、サーバー境界、画面所有者、世代・期限などの固定条件は解除しない。遠隔操作の実行条件と停止中キューの閲覧対象は、本体統合時に既存セッションの整合性条件と合わせて確定する。

## 制限と設定検証

追加ポリシーは最大100件、1件8KiB、合計64KiBとする。ロールは最大250件、ポリシーIDはASCII英数字と`._-`で最大64文字とし、`builtin.`は予約する。同じIDは重複不可。追加設定は1項目につき1つのCedarポリシーとする。

起動時には全ポリシーを構文・厳格スキーマ検証する。構文や型のエラーで部分適用しない。診断には安全なポリシーIDと失敗分類だけを返し、ポリシー原文は出力しない。実行時にもリクエスト・Entityを検証し、評価診断に1件でもエラーがあれば拒否する。

この制限で複雑な式の評価時間を保証するものではない。設定者は信頼された運用者に限定する。設定版はプリセット・ロール割当・ポリシー内容から計算し、ログに原文を含めずに評価時の設定を識別する。

## 設定形式

認可設定はサーバーごとの`servers.<名前>.authorization`に置く。省略時のpresetは`collaborative`、追加ルール・DJロールは空とする。将来複数Botを管理するときにも、サーバーの運用方式を同じ場所で定義できる。

```yaml
servers:
  home:
    id: "123456789012345678"
    bots: [main]
    command_bot: main
    authorization:
      preset: dj
      dj_role_ids: ["234567890123456789"]
      policies:
        - id: forbid_stop
          policy: |
            forbid(principal, action == Action::"playback.stop", resource);
```

これは形式の例であり、既存設定を置き換える指示ではない。ルールはYAMLの文字列として記述し、他の設定と同じ変数展開規則を適用する。外部ポリシーファイルや実行中の変更には初期版では対応しない。不明なキー、数値で記述したロールID、不正な構文・スキーマは設定読込時に拒否する。エラーにはルール本文を含めない。
