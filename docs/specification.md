# 現行仕様・要件

接続・動作設定はYAMLを使用する。[設定ファイル仕様](configuration.md)を参照。現在は1Bot・1サーバーに限定し、複数指定を拒否する。

2026-11-02時点の実装を基準とする。利用者から見た動作の参照先は本書とし、過去の検証結果は[文書一覧](index.md)から参照する。

## 対応範囲とURL

YouTube Data APIによるタイトル補完を任意で有効化できる（既定は無効）。指定言語の公式メタデータを単曲・リスト・Mix・自動再生候補の表示へ共通適用し、障害時はyt-dlpのタイトルで追加・再生を続ける。保存したタイトルは再生時・管理再起動時も維持する。[設定と制限](configuration.md#youtube-data-apiによるタイトル補完)を参照。

YouTube / YouTube Musicのメタデータは既定で日本語を優先する。`sources.youtube.metadata_language`で変更でき、単曲・プレイリスト・Mix・自動再生候補へ適用する。提供されない言語への翻訳は行わない。保存済みの曲名は維持する。[設定仕様](configuration.md)を参照。

主な用途はDiscord通話中のBGM。対象サイトはYouTube、YouTube Music、ニコニコ動画。取得対象は公開・限定公開として取得できる通常動画。ニコニコ動画に限り、CookieファイルまたはID・パスワードでログイン必須の通常動画にも対応する。認証は任意で既定は無効。ライブ中・配信予定・有料・会員限定動画、YouTubeの認証は対象外とする。[ニコニコ動画の認証](niconico-auth.md)を参照。

YouTubeの通常動画・Shorts・短縮URL、YouTube Musicの動画、ニコニコ動画の`sm` / `nm` / `so`形式と短縮URLを扱う。通常プレイリストの取り込みはYouTube / YouTube Musicに限る。

yt-dlpへ渡す前にURLを再構築する。動画ID、取り込みに使うリストIDだけを用途に応じて保持し、`si`、`utm_*`、`index`、再生開始時刻などの追加パラメーターとフラグメントは引き継がない。HTTP入力もHTTPSの正規URLへ変換する。認証情報・明示的なポート・ローカルファイル・未対応サイトのURLは受け付けない。

## コマンドと操作

操作はサーバー別の認可設定で制御する。既定の共同操作では参加者が曲追加と再生操作を行える。`dj_control`では一般参加者は曲追加・閲覧、DJロール・Discord管理者・所有者は再生操作も行える。`dj_control_self_skip`は一般参加者にも自分が手動追加した再生中の曲のスキップを許可する。`dj_only`では一般参加者は閲覧のみで、曲追加・再生操作はDJ等に限る。旧名`dj`は廃止した。追加ルールで許可・拒否を定義でき、明示的拒否を優先する。管理者も認可ポリシーを迂回しない。[許可表と詳細](authorization-model.md)を参照。

音楽情報の閲覧には対象VCのDiscord閲覧権限が必要。履歴は参加中VCに限定し、本人専用画面の所有者・期限・世代条件は追加許可でも解除できない。曲取得後などの状態変更直前にも認可を確認する。拒否は本人だけに案内し、事実取得や評価に失敗した場合は操作しない。

曲名リンクは共通で太字表示する。待機曲・自動再生候補は番号付きの2行構成で、補足行をインデントし曲間の空行を入れない。通常キューのフッターは「待機N曲 · 合計時間」（不明曲があれば既知分と不明件数）と、次行のページ情報を表示する。

Mix追加結果は「MixからN曲を追加しました」「起点：曲名リンク」と曲の詳細・サムネイルを表示する。プレイリスト追加結果はリスト名（取得済みの場合）または「プレイリストを開く」のリンクを示す。付属リストでは「最初に追加した曲：曲名リンク」と詳細・サムネイルも残す。件数は今回の追加分のみで、既に追加した単曲を含めない。プレイリスト自身の画像は現在取得しておらず、直接のリスト追加で先頭曲の画像を代用しない。

毎曲の再生準備・再生開始通知は送信しない。単発の取得・再生失敗は曲名と次の動作を通知し、音声送信に成功するまでの連続失敗は同じ通知メッセージを更新する。通知先チャンネルが変わった場合も新しい通知とする。3曲連続失敗による停止・自動再生OFF・候補取得失敗によるOFFは最終状態を通知する。通知は再生処理とは別に送り、送信失敗はログへ記録して音楽処理の失敗として扱わない。送信待ちが滞留した場合は最新の状態を優先し、再生が進んだ後の古い失敗や移動前のVC向けの通知は送信前に除外する。

専用チャンネルへ再生曲のみを投稿する任意の再生ログ機能は将来要件とし、現在は未実装。設定キーや投稿処理はまだ提供しない。

メッセージは[UI設計指針](ui-guidelines.md)に従う。単曲・リスト・Mixの追加結果は曲やリストへのリンクを含むEmbedで表示し、通常の除外集計は省略する。追加数が0なら成功見出しを使わない。部分成功は黄色、失敗は赤色とし、キューに保持した範囲と必要な対処を示す。停止・スキップ・音量変更・自動再生ON/OFFは短いテキストで応答する。

`/queue show`の表示、`/nowplaying`、値を指定しない`/volume`、`/autoplay status`は本人限定。状態変更は原則公開するが、キュー編集・全消去の確認と結果は本人限定とする。入力・VC権限を処理開始前に確認し、違反は本人にだけ知らせる。公開の処理中応答後に失敗した場合は元の応答を更新する。状態確認は表示時点のスナップショットで、定期更新しない。単曲表示は曲名160文字、キューの待機曲・自動再生候補はUnicode幅で曲名56・チャンネル名24を上限に省略する。書記素の途中で切らず、曖昧幅は1に固定する。キュー内の再生中曲名は従来の60文字とする。サーバー内の名前はメンションで表示し、通知は抑止する。

API補完で取得したチャンネル名は、キュー・自動再生候補・再生中表示にリンクとして表示する。「投稿：」「追加：」は付けず、Discordの追加者はユーザーメンションだけを表示する。キューには画像を表示せず、`/nowplaying` には現在曲のサムネイルを表示する。チャンネル名は投稿者情報であり、アーティスト名とは扱わない。情報がない項目は省略する。長いチャンネル名は表示時に省略し、Markdownをエスケープする。

再生時間は有効なyt-dlpの値を優先し、欠落・不正な場合のみData APIで補完する。どちらでも取得できない場合は時間不明。通常キューの合計は既知の時間のみ集計し、不明な曲があれば「既知分…／時間不明…曲」と明示する。自動再生候補の合計件数・合計時間は表示しない。時間は表示用途であり、再生の終了判定には使わない。

Botは設定した1サーバーで動作する。追加・再開・停止・スキップ・キュー消去・音量変更・自動再生のON/OFFは、利用者が音声チャンネルに参加していることを確認する。Botが接続中なら同じチャンネルから操作する。キュー・再生中の曲・音量・自動再生状態の参照は、音声チャンネルへの参加を必要としない。リスト取り込みボタンには追加者本人の確認もある。

| コマンド | 動作 |
| --- | --- |
| `/play url:URL` | 単曲またはプレイリストを追加し、再生開始 |
| `/playnext url:URL` | 単曲を自分の待機曲の先頭に追加。URL必須 |
| `/play` | 保持している待機キューを再開 |
| `/mix url:URL count:20` | 動画を起点にMixを追加。起点を含め既定20曲、1〜50曲 |
| `/stop` | 再生中の曲を終了して切断。待機キューは保持 |
| `/help page:…` | 本人専用の使い方ガイド・コマンド詳細。pageは候補検索付きの任意指定。省略時は基本画面 |
| `/skip` | 次の曲へ移動 |
| `/queue show page:1` | 本人専用のEmbedで再生予定順を10曲ずつ表示。ページ送り・更新ボタン付き |
| `/queue edit [user]` | 本人専用の編集画面を直接表示。追加者の指定は任意 |
| `/queue clear` | 本人専用の確認画面で確定後、手動の待機キューを全消去 |

| `/autoplay on` | 手動キューが空のときの自動補充を有効化 |
| `/autoplay off` | 補充を停止。現在再生中の曲は継続 |
| `/autoplay status` | ON/OFF、起点、取得状態を本人限定で表示 |

## 自分の次の番への追加

キュー表示の詳細は[キューの表示と操作](queue-display.md)を参照。手動の待機曲がなければ、自動再生ON時は取得済み候補の一覧へ切り替える。再生中の曲は一覧とは別に表示する。表示操作は選曲・候補取得・候補の消費を行わない。

`/queue edit [user]`または手動待機曲があるときの「キューを編集」から、追加者別の編集一覧を開ける。対象VCへの参加と曲単位の権限を確認し、上・下・先頭・指定位置への移動と単曲削除を行う。移動は同じ追加者の待機曲内だけに適用し、他の追加者との巡回順を維持する。再生中・準備中の曲、自動再生候補は編集対象外。編集画面と結果は本人限定で、公開通知を送らない。詳細と検証状況は[キュー編集要件](queue-edit-plan.md)を参照。

`/playnext`は自分の待機曲の先頭へ単曲を追加する。再生中の曲は中断せず、他の追加者との交代順も変更しない。自分に待機曲がない場合は通常の追加と同じ規則で巡回に参加する。X、Yの順に連続して先頭追加すると、自分の曲列は`Y → X → 既存曲`となる。

A1が再生中で、待機順が`B1 → A2 → B2 → A3`のときにAさんがXを追加すると、待機順は`B1 → X → B2 → A2 → A3`となる。追加完了メッセージにも、自分の待機曲の先頭への追加であり、他の追加者との交代順を維持することを表示する。

単曲に付属するリストは追加後のボタンで取り込める。リスト専用URLを直接先頭追加する操作と、`/mix`の先頭指定は対象外。取得失敗時はキューを変更しない。容量・操作権限・永続化は通常追加と共通で、実際に再生されたYouTube曲は自動再生の起点にもなり得る。

付属リストは取り込み確定時に元の曲が待機中ならその直後へ挿入する。元の曲が再生中・再生済み・削除済みなら、`/playnext`由来は自分の先頭、`/play`由来は末尾へ追加する。詳細は[リスト追加](playlist-button.md)を参照。

## プロフィールの再生中表示

`bots.<name>.activity.enabled`は既定で`true`。設定対象と実際の参加先が同じ1サーバーの場合に限り、BotのListeningアクティビティに曲名を表示する。設定外サーバーへの参加、参加状況が未確定・利用不可の場合は表示を消す。将来複数サーバーを設定したBotも、現在の再生数に関係なく表示しない。再生数などの集約表示も行わない。

音声送信開始後に表示し、準備中・終了・スキップ・停止・切断時は消去する。曲名は最大128文字に省略する。Presenceはサーバー限定公開ではない。更新は1秒間隔で最新状態を確認し、送信間隔は最低5秒。反映にはこの待ち時間とDiscord側の遅延が生じる。更新失敗は再生に影響させず、最新状態で再試行する。起動・Gateway再接続時も再計算し、表示内容は保存しない。

## 音量・ビットレート

音声のOpus目標ビットレートは接続先チャンネルの`bitrate`に従う。再生開始時と各20msフレームの変換前に最新のチャンネルキャッシュを参照し、再生中の設定変更も反映する。取得できない場合はその曲で直前に適用した値を維持し、初回から取得できない場合は96kbpsを使う。有効範囲は8〜384kbps。CVBRを使うため、パケットごとのサイズは一定ではない。

音量は既定の初期値が30%（−28 dB、振幅比約0.0398）です。1〜100%を−39.6〜0 dBへ線形に対応させ、0%はミュートとします。変更時には10msのフェードを適用します。音源ごとのラウドネス正規化は行いません。

1〜100%の値をpとすると、`dB = 40 × (p / 100 − 1)`、振幅倍率は`10^(dB / 20)`です。50%は−20dB（振幅10%）になります。100%を超える増幅は行いません。設定は送信直前の20msフレームに適用し、連続操作では最新の設定を使います。Discord側のバッファーや端末の遅延は別に生じます。

## 公平キューと再生順

手動追加曲は追加者ごとに追加順を維持し、追加者同士で1曲ずつ交代する。再生開始時にその人を巡回順から取り出し、曲の終了時に残曲があれば最後尾へ戻す。再生中の人が追加しても次の順番を先取りしない。新しい追加者は現在待っている追加者の最後尾に入る。既に待機中の追加者は、その人の曲列に追加するだけで巡回順を変えない。

AさんのA1が再生中で、A2・A3が待機している例では、次の順になる。各行は別の状況を示し、以後の追加がないものとする。

| A1の再生中の状況 | A1終了後の順番 |
| --- | --- |
| 他の人の曲がない | A2 → A3 |
| BさんがB1・B2を追加 | B1 → A2 → B2 → A3 |
| Bさんの追加後にCさんがC1を追加 | B1 → C1 → A2 → B2 → A3 |

再生中の曲へは割り込まない。公平性は曲数単位で、曲の長さや過去の累計再生時間は配分に使わない。スキップ・通常の停止・再生失敗もその人の1回の順番を終える。プロセス終了による中断は後述の再起動復元として扱う。

単曲、通常プレイリスト、Mixからの明示的な追加はすべて手動追加に含める。自動再生曲はこの巡回に入らず、手動キューが空のときだけ選択する。`/queue show`の待機一覧は再生中の曲を除くが、順番の計算には再生中の追加者も考慮する。再生中の曲は別欄へ表示する。新しい追加によって表示後の予定順は変わり得る。

待機キューは既定で全体500曲、1回のプレイリスト取得は先頭100項目までです。追加者内では追加順を保ち、追加者同士をラウンドロビンで再生します。手動追加曲が3曲連続で取得・再生に失敗すると再生処理を停止し、自動再生をOFFにします。失敗した曲は取り除き、残りの待機曲とVC接続は保持します。URLなしの`/play`または新しい曲の追加で再開し、連続失敗回数はリセットします。通知には停止理由と再開方法を表示します。通知失敗だけを理由に切断しません。

人がいる間は、曲の終了、キューの枯渇、連続失敗、自動再生OFFを理由に既定ではVCから退出しません。`playback.disconnect_when_idle: true`を明示した場合のみ、再生待ち・エラー停止で60秒経過すると切断します。Bot以外の参加者がいない状態が60秒続くと、設定に関係なく切断します。判定は5秒間隔です。`/stop`、管理停止・再起動、外部からの切断では従来どおり接続を閉じます。外部切断から自動で入り直しません。外部切断時も現在曲と再生設定を保持し、再開操作を待ちます。手動追加キューは変更ごとに保存し、再起動後も追加者と順番を復元します。ボタンの状態は再起動で失われます。

Botが別のVCへ移動された場合は、再生中の曲・位置・キュー・音量・自動再生設定を維持し、移動先を操作権限の基準にします。移動元の無人タイマーを破棄し、移動先が無人なら改めて60秒を数えます。音声切り替え中は同じOpusパケットの送信を待機し、再生位置を進めません。所属・接続先情報と通信暗号鍵・DAVEの準備を含めて30秒以内に復旧できない場合は再生を停止し、現在曲・待機キュー・音量・自動再生設定を保持します。重複通知・内部リトライ・復旧中の再移動では期限を延長しません。接続の失敗は曲の連続失敗に数えず、次の曲へ進めません。URLなしの/playで現在曲を先頭から再開します。復旧失敗後は自動再生がONでも、明示的な再開操作まで再生を進めません。通信断やDiscord側による切断まで接続維持を保証するものではありません。

一時的な通信断では既存セッションのResumeを優先し、失効時は新規接続へ進みます。参加通知が5秒以内に揃わない場合は権限を確認し、退出完了を確認してから一度だけ再入室します。通知が揃って接続処理を開始した後の失敗では、追加の退出・再入室を行わず停止します。再入室後も通知待ちは5秒まで、接続処理は復旧全体の残り時間までです。自動再入室は直近5分で2回までです。外部退出や明示停止に反して再参加しません。復旧失敗後のURLなし`/play`も接続の作り直しを行えるため、通常は`/stop`を先に実行する必要はありません。詳細は[音声接続管理](voice-connection-plan.md)を参照してください。

移動前に開始した曲の履歴は移動元VCに残し、移動を理由とした履歴の複製・移動は行いません。次に再生開始した曲から移動先VCに記録します。移動元の履歴画面は移動先へ転用せず、`/history`を開き直します。移動時に自動通知先を解除し、移動先の参加者がコマンドを操作したチャンネルを新しい通知先にします。解除後に移動元へ通知を送り続けません（既に送信中のリクエストは取り消せません）。

失敗後の明示的な再接続では、Botがまだ所属していると確認できれば退出完了を待って再参加し、退出済みなら通常の参加を行います。所属を確認できない場合は最大5秒確認し、判断できなければ停止します。要求したVCが設定されていることだけでは、参加済みとは扱いません。

## 停止・再起動と永続化

URLなし`/play`は、既に再生中・準備中・復旧中の場合はその状態を返し、二重に開始しない。新しい再開要求は接続完了を待たず受け付け、最初の音声送信成功後に元の応答を「再開しました」へ更新する。取得失敗後に次の曲へ進んだ場合も、実際の音声送信まで成功と表示しない。再生対象なし、音源失敗、接続失敗、停止・スキップはそれぞれ結果を返して準備中の表示を終了する。受付後のVC移動では再生処理を継続し、旧VC向けの応答更新だけを終了する。外部退出は要求を中止する。応答更新に失敗しても再生は停止しない。

閲覧用の再生履歴を`runtime.state_dir/history.sqlite`へ記録する。最初の音声送信成功で記録し、管理再開時には再生単位IDと元の開始日時を維持する。保存は別処理で行い、保存待ちは最大128件、各保存は2秒以内・最大3回試行する。保存失敗や滞留超過はログへ残し、音声再生は継続する。管理終了は保存を最大10秒待つが、異常終了や期限超過では未保存分が失われ得る。既存の自動再生用履歴は別に保持する。

`/history`は参加中のVCを対象に本人専用で表示する。画像なし・新しい順・10曲単位とし、中央のページ番号ボタンから番号を入力できる。更新すると最新の1ページ目へ戻る。保持上限による削除で閲覧開始時の並びを維持できなくなった場合は更新を案内する。各操作で本人・元のVCへの参加・画面の操作世代と15分の期限を確認する。

表示ページから1曲を選び、通常追加または自分のキュー先頭への追加を行える。再追加では最新の単曲情報を取得し、操作した人を追加者として扱う。付属リストは取り込まず、過去の記録は書き換えない。再追加結果も本人限定とする。詳細と実Discordでの検証状況は[履歴コマンドの要件](history-plan.md)を参照。

ページ番号の入力欄には有効範囲を表示する。不正入力時は本人専用のエラーメッセージに［入力し直す］ボタンを表示し、再入力に成功したら元の履歴画面を更新する。Discordのモーダル内へ独自の入力エラーを表示する方式は採用しない。

管理チェックポイントの書き込み・同期中に再生状態や設定が変わった場合、古い保存内容の確定を拒否してBotを維持します。管理再起動を再実行すると最新状態で保存を試します。保存中も状態照会や操作を受け付け、保存確定後は変更を拒否します。

管理チェックポイントの保存確定後は、追加・キュー消去・音量変更・自動再生設定・停止・スキップを再起動処理中として拒否する。読み取り操作は引き続き許可する。

音声接続中も停止と管理状態照会を受け付けます。初回接続・再接続・自動復旧中の曲追加は、通常の権限確認と容量制限の下で受け付け、追加を理由に別の接続処理を開始しません。切断の後処理中に追加した曲もキューに保持します。停止・キュー消去・管理終了の後に古い接続が成功しても再生は開始せず、接続を破棄します。

管理再起動で同じ再生を再開した場合、直近の再生履歴へ重複登録しません。音声送信前の再起動を繰り返した場合も、この区別を保持します。同じ動画を改めて追加した場合は別の再生として記録します。旧版のチェックポイントには再生単位の識別情報がないため、この保証は新版で保存した状態から適用します。

自動再生の音声送信開始前に手動曲が追加された場合は手動曲を優先します。中断した候補は起点が変わっていなければ候補の先頭へ戻します。起点変更・自動再生OFF・明示スキップ・取得失敗では戻しません。既に音声送信を開始した曲はこの対象外です。

空の追加要求やキュー上限による全件未追加では、保存済みのキューを再書き込みしません。ただし、直前の保存が失敗している場合は、変更がない追加要求でも現在のキューの保存を再試行します。

管理タスクの`bot-restart`は再生／停止状態、音量、自動再生ON/OFF・有効化者・起点・直近50曲の履歴、音声・通知先チャンネルを保存します。再生中だった場合は接続先へ再接続し、曲の先頭から再開します。自動再生中の曲も自動再生がONなら再試行しますが、手動キューを優先します。停止中は停止状態を維持します。再生位置、取得済み音源、未再生の自動再生候補、ボタン状態は復元しません。`/stop`や`/skip`で明示的に止めた曲は再開対象に含めません。

`bot-stop`も設定を保存しますが、続く`bot-start`は自動再接続せず、URLなしの`/play`で再開します。保存失敗時は管理タスクが停止を拒否します。異常終了時や旧版からの初回移行では追加状態を保存できず、手動キューのみの復元になる場合があります。接続失敗時はキューを保持し、`/play`で再試行できます。

保存先は既定で`.asterinmusic/state/<アプリID>-<サーバーID>-queue.json`です。YAMLの`runtime.state_dir`で変更できます。開発環境は従来の`.dev/state`を明示指定しています。同じ保存先を複数のBotプロセスで同時使用しないでください。曲情報・追加者情報を含むため、Git管理外の場所を指定してください。保存は一時ファイルの同期後に置換します。破損した保存ファイルがある場合は起動を中止し、そのファイルを保持します。保存に失敗した場合はログに記録し、メモリ上のキューを維持しますが、最新変更の復元は保証できません。旧版のメモリ内キューは初回移行時に復元できません。

## プレイリストとMix

動画とリストの両方を含むURLは最初に単曲だけを追加し、追加完了メッセージのボタンで残りを取り込みます。[詳細仕様](playlist-button.md)を参照してください。

Mix付き動画URLでは「Mixから追加（最大20曲）」ボタンを表示します。ボタンは追加済みの起点を除外し、重複しない候補を最大20曲追加します。`/mix`はMixのない動画URLでも生成を試み、既存のMixがあればそちらを使用します。起点の動画を先頭に含め、指定件数まで追加します。対象はYouTube / YouTube Musicの動画URLです。

Mixの候補は先頭100件まで取得し、取り込み内では動画IDで重複を除外します。既存キューとの重複は許可します。取得できた曲は実行者の曲列に追加し、公平な順番で再生します。曲目・曲順はブラウザと異なる場合があり、自動補充は行いません。Mixを取得できなければ単曲追加へ切り替えず、キューを変更しません。

## 自動再生

自動再生はサーバー単位で既定OFFです。有効な間に最後に音声送信が始まった、手動追加のYouTube／YouTube Music曲を起点にMix候補を取得します。通常プレイリスト、`/mix`、Mixボタンから取り込んだ曲も手動追加として扱います。自動追加曲とニコニコ動画は起点を変更しません。有効化時に対象の手動曲を再生中ならその曲を採用し、それ以外は起点待ちになります。

候補は手動キューとは別に保持し、手動キューが空のときだけ1曲ずつ再生します。取得・再生準備中に手動追加があれば手動曲を優先し、既に自動追加曲の再生が始まっていれば、その曲の終了後に切り替えます。直近50曲の再生履歴と候補内の動画ID重複を除外します。履歴は手動・自動の両方を含み、OFF→ONや起点変更でも保持します。

曲数・時間・無操作時間の上限は設けません。候補取得は最大100件・45秒で、候補を選べなければ追加でもう1回だけ取得し、それでも選べなければOFFにします。自動追加曲が3曲連続で失敗した場合もOFFにして通知します。`/stop`、切断、無人状態60秒でOFFになります。管理タスクの再起動では保存状態を復元します。起点待ちの空キューも再生待ちの退出設定に従い、既定では切断しません。候補取得中は取得タイムアウトで判断します。

`/queue clear`は手動キューだけを消去し、自動再生の状態は変更しません。`/autoplay off`は未再生候補と取得処理を破棄します。起点が変わったときも古い候補を破棄します。`/nowplaying`では自動追加曲を「自動再生」と表示します。

## 取得・再生の制限と失敗時の動作

| 項目 | 現在の値・動作 |
| --- | --- |
| 待機キュー | 既定で全体500曲。再生中の曲は別枠 |
| 再起動時の中断曲 | 待機列の先頭へ戻すため、一時的に501曲になる場合がある。容量が空くまで追加不可 |
| 通常プレイリスト | 先頭100項目まで。取得不能項目や起点除外分を101項目目以降で補充しない |
| Mixの候補取得 | 先頭100候補まで。追加件数はボタン20曲、コマンド既定20曲・最大50曲 |
| メタデータ取得 | 既定45秒のタイムアウト |
| 音声の先読み | 1曲256MiBまでの一時ファイル。取得完了を待たず読み出す |
| 音声接続・DAVEの復旧 | 全体で最大30秒。失敗時は現在曲・設定を保持して停止し、明示的な再開を待つ |
| DAVE送信コールバックの失敗 | 暗号状態の継続を保証できないため、同じ接続をResumeせず保持停止する。URLなし`/play`で新しい接続を作る |
| 単曲の取得・再生失敗 | 通知して次へ進む。手動再生で3曲連続失敗すると停止し、残りを保持 |
| プレイリストの部分失敗 | 取得できた項目を追加し、一部取得できなかった旨を補足 |
| 音声接続失敗 | 追加済みの手動曲をキューに保持し、再開を待つ |

取得不能件数はyt-dlpが返した情報から検出できた範囲であり、サイト上の全削除項目の件数を保証しない。先頭100項目を取得した場合は、それ以降の存在を確認できなくても上限到達として表示する。

`/nowplaying`の経過時間は音声送信側の進行であり、利用者の端末で聞こえた時刻とは一致しない。鍵交換待ち・通信・端末バッファーによる差が生じる。

## 更新と運用の要件

yt-dlpの最新版を起動時と24時間ごとに確認し、ログへ記録する。適用は自動では行わず、運用者が検証・選択した版を次回起動時から使う。更新・切り戻し手順は[開発・運用手順](development.md)に記載する。

開発はWindows/Linuxに対応し、依存バージョンはmise.lockおよびgo.mod/go.sumで固定する。起動・停止は管理タスクを使用し、重複起動や確認不能なプロセスに対して追加起動・自動強制終了で対処しない。標準Bot本体はCGO非依存とし、外部コマンドとの境界は[アーキテクチャ](architecture.md)に記載する。

## 自動再生候補の先行取得

自動再生ON・起点あり・手動待機曲なし・利用可能候補なしの場合、音声送信開始後に候補メタデータを先行取得する。自動再生ON操作とキュー消去時にも条件を確認する。先行取得は1補充につき1回までで、失敗しても現在曲を中断しない。選曲時には同じ取得の完了を待ち、先行取得を含め最大2回で使える候補が得られなければOFFにする。手動追加・起点変更・OFF・停止時は不要な取得を無効化する。音声は選曲後に取得する。

## 対象外と未検証条件

開発用の管理再起動は`--after-track`で次曲の音声送信開始まで待機できる。待機はビルド・事前検証後から開始する。次曲の冒頭を短く送信した後に切断・再接続し、その曲の先頭から再開する。再生停止時は待機を終了して再起動する。シームレスな音声継続や再生位置の復元は行わない。

現在の対象外は、Spotify、ニコニコ動画のリスト一括取り込み、YouTubeのログイン必須コンテンツ、有料・会員限定コンテンツ、ID・パスワード方式での追加認証、ライブ配信、文字列検索、シーク・一時停止、音源ごとのラウドネス正規化。新しい機能として合意するまでは対応済みと扱わない。

実装済みでも、YouTube Music専用カタログ・プレイリスト、多人数での連続入退室、長時間運転、Linuxからの実Discord接続などは検証範囲に制限がある。Pure Go DAVEの相互運用・Windowsでの再生と再参加は確認済みだが、第三者のセキュリティ監査を代替するものではない。具体的な条件と測定結果は[検証記録一覧](index.md)を参照する。

## 運用ログ

運用ログは利用者向けメッセージ・再生履歴DBとは別に、標準エラーへ出力する。既定はINFO・textで、設定ファイルからレベル、text／json形式、コンポーネントごとのレベルを選択する。設定例と対象一覧は[設定ファイル](configuration.md#ログ設定)、閲覧と保持は[開発・運用手順](development.md#ログの確認)を参照する。

曲名・入力URL・ユーザー名・認証情報は通常のログに含めない。再生開始は最初の音声送信成功に対応し、同じ再生試行の開始・終了・音声統計を`playback_id`で関連付ける。操作は`operation_id`で追跡する。現在の移行範囲と未検証事項は[ログ改善の要件](logging-plan.md)に記録する。

## 任意のトレース計装

OpenTelemetryトレースは任意で、既定は無効。音声接続・VC移動・復旧・管理再起動後の再生復元を対象に、通知待ち、通信確立、DAVE準備、最初の音声送信までの区間と結果を記録する。通信確立はWebSocket接続、Hello、Identify/Ready、UDP探索、プロトコル選択、SessionDescription、通信鍵設定、DAVE準備の段階を区別する。通常の曲取得や20msごとのフレームは計装しない。

有効時は設定したOTLP/HTTP送信先へ非同期に送信し、関連するログにtrace/span IDを付ける。送信先の停止・バッファ満杯ではトレースを失う場合があるが、再生を待たせず、既存ログは継続する。曲名・URL・認証情報・エラー原文は記録しない。設定は[設定ファイル](configuration.md)、ローカル閲覧と削除は[開発手順](development.md#ローカルのトレース閲覧)、対象と観測限界は[アーキテクチャ](architecture.md#運用ログ)と[検証記録](tracing-verification.md)を参照する。
