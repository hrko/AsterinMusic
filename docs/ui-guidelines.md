# BotメッセージのUI設計指針

## 目的と適用範囲

AsterinMusicは通話中のBGM用途を想定する。操作結果がすぐ分かり、会話を妨げないことをメッセージ設計の基準とする。本書は今後のUI変更の判断基準であり、すべてが実装済みであることを示さない。現在の挙動は[現行仕様](specification.md)、今回の適用案は[UI変更案](ui-message-plan.md)を参照する。

提示された画面では、大きなリンクプレビュー、同じ曲の準備通知の反復、正常なMix取り込みに付く多数の集計・注意書きが、結果の把握を難しくしていた。重複通知の原因は画面だけでは断定しない。表示の改善と通知を送る条件の改善を両方扱う。

## 情報の選択

優先順位は、操作結果、対象、必要な次の操作とする。各項目が利用者の判断にどう役立つか説明できない場合は、通常の応答に含めない。

| 情報 | 表示方針 |
| --- | --- |
| 結果 | 必ず表示する。実際に追加できた件数や変更後の値を使う |
| 対象 | 識別に必要な曲名・リスト名・起点曲などを表示する |
| 次の操作 | 再試行や追加取り込みなど、その場で必要な場合だけ示す |
| 意図した結果との差 | 容量不足や取得失敗など、実際に差がある場合だけ補足する |
| 内部処理 | API経路、候補取得数、内部の重複除去などは原則ログへ残す |
| 一般的な説明 | コマンド説明、文書、操作前の短い案内へ置く。成功時に繰り返さない |

0件の除外・失敗を列挙しない。Mixの指定件数を超えた候補や意図的な起点除外は通常の成功に含め、「未追加」として警告しない。取得できなかった件数が不明なら正確な数値に見せず、「一部の曲を取得できませんでした」とする。部分成功は成功した範囲と残った問題を分け、全成功や全失敗に見せない。

## Embedとテキスト

| 内容 | 形式 |
| --- | --- |
| 曲追加・リスト追加の結果 | 対象と結果をまとめたコンパクトなEmbed。必要ならボタンを付ける |
| キュー・再生中・自動再生の状態確認 | 複数項目を参照するEmbed |
| 停止・スキップ・音量変更・ON/OFFの成功 | 1文程度のテキスト |
| 単純な入力・操作条件エラー | 短いテキスト |
| 部分成功・影響や復旧方法の説明が必要な失敗 | 結果、影響、対処を分けたEmbed |

長文だからEmbedにするのではなく、複数項目を整理する必要があるかで選ぶ。結果は見出しまたは文頭に置く。小さなフッターには補助情報だけを置き、必要な復旧操作を隠さない。

## 曲情報の共通表現

曲一覧では、曲名の行末に半角スペース2個を付けて改行し、ページ先頭の番号幅に固定してインデントした補足行を `-# ` で始める。単一改行だけでは連結され、空行では余白が過大になるため、この書式を使う。描画はDiscord実画面で確認する。

曲名リンクは太字とする。通常キューと自動再生候補の補足情報はsubtext、再生中の曲や単曲の結果表示の補足は通常の文字サイズとする。一覧は順序付きリストで各曲を並べ、補足行を同じ項目内へインデントし、曲間の空行を置かない。セクション間には余白を残す。件数と合計時間は同じ行、ページ情報は次の行に配置する。自動再生候補には総件数・合計時間を表示しない。

取得済みなら実際の曲名・リスト名をリンク名に使う。「起点」は曲名リンクの前にコロンで添える。表示のための追加通信は行わず、付属リストの結果には最初の単曲情報を保持して再利用する。Discord上の順序付きリストのインデント・長い曲名の折り返しは、実画面でも確認する。

曲名リンクを主情報とし、その下に「時間 · チャンネルリンク · ユーザーメンション」を置く。「投稿：」「追加：」は付けない。自動再生曲はユーザーの代わりに「自動再生」、自動再生候補一覧では見出しで由来を示し、各行で繰り返さない。

生URLを並べず、曲名をリンクにする。チャンネルが分かる場合はサイト名を重ねない。画像は右側の小さなサムネイルとし、キューでは画像を表示しない。大きな画像や自動リンクプレビューを発生させない。情報がない項目は省略するが、集計に影響する時間不明は明示する。

単曲表示はキューの各行より長い曲名を許容する。データを切り詰めず表示時だけ省略し、Markdownをエスケープする。名前はメンションで表現するが、意図しない通知は発生させない。モバイル幅、長い日本語・英語の曲名、情報欠落を前提に確認する。

経過時間を継続更新しない画面では「表示時点 0:49 / 5:20」など時点を明示する。API利用の有無など取得の内部事情は表示しない。

## 公開範囲と通知条件

公開範囲はEmbedかテキストかとは独立して選ぶ。状態の確認は原則本人限定、共有状態を変える操作結果は公開とする。入力不正・VC条件違反・ボタンの権限違反は本人限定とする。再生停止や自動再生OFFなど、参加者が知る必要のある障害は公開する。

自動の曲変更通知は既定で送らず、状態確認コマンドとアクティビティで確認する方針を推奨する。通知を将来選択可能にする場合は、音声送信の開始を基準にする。取得開始・再試行・再接続・管理再起動を別の再生開始として通知しない。具体的な変更時期と公開範囲は変更案で確定する。

## メッセージの更新と失敗

1操作の進行は可能な限り同じメッセージで表す。ボタン操作は元のメッセージを取得中から結果へ更新し、通常の待機にはDiscordの処理中表示を使う。内部リトライは通知を増やさない。同一原因による連続失敗は集約し、停止や機能OFFなどの最終結果を明示する。

完了して使えなくなったボタンは削除する。再試行可能な失敗ではボタンを残すが、期限や権限は維持する。失敗を成功として見せず、キューに追加済みか、再生を継続するか、利用者の操作が必要かを伝える。内部エラー原文や英語の実装用メッセージはそのまま表示しない。

## 装飾

通常の情報・成功は青系、部分成功・注意は黄系、操作失敗・停止を伴う障害は赤系を使う。色だけに依存せず見出しで結果を伝える。Bot名・ロゴは各Embedで繰り返さず、絵文字は必要な場合だけ補助的に使う。

## 変更時の確認項目

- 何が起きたか、対象は何かが文頭で分かるか。
- 誰が知る必要がある情報か。公開範囲は適切か。
- 利用者が要求した範囲と内部の取得範囲を混同していないか。
- 次の操作が必要なら具体的に示しているか。
- 同じ内容の通知や、0件の集計・一般的な注意書きを繰り返していないか。
- 既存メッセージの更新で済むか。
- 長い名前、情報欠落、部分成功でもレイアウトと意味が保たれるか。
- 表示時点の状態と、リアルタイム更新を区別できるか。
