# 待機キュー編集の要件

本書は待機曲の削除・並び替えについて、実装前の合意事項をまとめる。未実装であり、現在の挙動は[現行仕様](specification.md)と[キュー表示](queue-display.md)を参照する。実装時には現行仕様、認可モデル・操作棚卸し、help、および必要なアーキテクチャ記述を更新する。

## 対象と操作の意味

手動追加された待機曲を対象とする。プレイリスト・Mix・履歴から明示的に追加した曲も含む。再生中・再生準備中として待機キューから取り出された曲、自動再生候補は対象外とする。再生中の曲を止める操作は既存のスキップを使う。

並び替えは同じ追加者の待機曲内に限定する。追加者や他の追加者の曲順、ユーザー間の巡回順を変更しない。先頭への移動も、その追加者の待機曲の先頭への移動であり、次の全体再生を保証しない。再生中の追加者を考慮する既存の巡回規則は維持する。

| 操作 | 結果 |
| --- | --- |
| 上へ・下へ | 選択曲を同じ追加者の一覧で1つ移動する |
| 先頭へ | 選択曲を同じ追加者の待機曲の先頭へ移動する |
| 順番を指定 | 移動後にその追加者の何曲目になるかを指定する |
| 削除 | 選択した待機項目1件を取り除く |

初期の編集UIは1曲単位とする。全体の自由な並び替え、追加者の変更、複数曲の同時編集、自動再生候補の編集は対象外。既存の全消去は別操作として維持し、新しい削除権限で全消去を許可しない。「自分の待機曲を全削除」は候補として残すが、今回の必須範囲には含めない。

## 認可

`queue.remove`と`queue.reorder`を別アクションとして認可サービスへ渡す。追加者IDと操作者IDの一致で本人の曲を判定し、自分用・他人用のアクションには分割しない。対象にはBot・サーバー・再生セッション・VC・キュー項目と追加者を特定できる情報を持たせる。Cedar固有の型はビジネスロジックへ持ち込まない。

| プリセット | 一般参加者：自分の曲 | 一般参加者：他人の曲 | DJ等 |
| --- | --- | --- | --- |
| `collaborative` | 削除・並び替え | 削除・並び替え | 全員の曲を編集 |
| `dj_control` | 削除・並び替え | 不可 | 全員の曲を編集 |
| `dj_control_self_skip` | 削除・並び替え | 不可 | 全員の曲を編集 |
| `dj_only` | 不可 | 不可 | 全員の曲を編集 |

DJ等は[認可モデル](authorization-model.md)の指定DJロール・管理者・サーバー所有者を指す。表は基礎プリセットの許可であり、追加の明示的拒否を優先する。削除のみ許可するなど、両アクションを独立して制御できるようにする。既存のスキップ権限は変更しない。

編集には対象VCへの参加と既存の閲覧・サーバー境界の条件を要求する。DJ等もVC参加の例外にはしない。画面所有者・対象セッション・操作世代・期限などの固定条件はポリシーで解除しない。表示時の許可を使い回さず、実行時に最新のVC・ロール・対象曲で再確認する。認可情報の取得・評価に失敗した場合は変更しない。

## 画面と選択状態

`/queue`の全体再生予定順と、追加者別の編集一覧を分ける。入口は「キューを編集」とし、本人専用の編集Embedを開く。編集画面内では曲選択後も一覧を維持し、別の曲詳細画面へ遷移しない。

見出しは「@追加者 の待機曲」とし、「順番の変更は、この追加者の待機曲内に適用されます」と短く案内する。名前はメンションで表し通知を抑止する。通常のキューと同じく画像なし、1ページ10曲、太字の曲名リンクとsubtextの補足行を使う。曲名・チャンネル名の省略は既存のUnicode幅による規則に従う。番号は追加者内でページをまたいで連番とし、全体再生順の順位と混同させない。

自分の曲だけを編集できる場合は追加者選択を出さない。他人の曲も編集できる場合は「追加者を変更」から専用の選択画面を開く。表示名と待機曲数を示し、同名の追加者を識別できる補足を付ける。候補はページ分けし、多数でも切り捨てない。追加者を選ぶと編集一覧へ戻る。初期表示は自分の待機曲を優先し、なければ編集可能な先頭の追加者とする。削除・並び替えのいずれかが可能な対象を選べるようにし、許可されない操作は無効化する。

操作対象は表示ページの曲選択メニューで1曲選ぶ。選択曲には番号の後、曲名の前に `▶` を置く。Markdownは `2. ▶ **[曲名](URL)**` の形とし、番号の前にマーカーを挿入しない。曲名行末の半角スペース2個による改行、ページ先頭の番号幅に固定した補足行のインデント、曲間に空行を置かない規則を維持する。マーカーの幅でインデントを変えない。

配置例（曲の補足は省略）：

```text
@追加者 の待機曲

1. 曲A
2. ▶ 曲B
3. 曲C

▶ 操作対象：曲B

[ 操作する曲を選択 ▾ ]
[ ↑ 上へ ] [ ↓ 下へ ] [ 先頭へ ] [ 順番を指定 ] [ 削除 ]
[ ◀ 前へ ] [ 1 / 2 ] [ 次へ ▶ ] [ ↻ 更新 ]
[ 追加者を変更 ] [ 再生キューへ戻る ]
```

未選択時は変更ボタンを無効化する。先頭での上移動・先頭移動、末尾での下移動など、位置が変わらない操作も無効化する。順番指定はモーダルで1〜その追加者の待機曲数を入力させ、移動後の位置を指定することを明示する。

ページ中央の「現在ページ / 総ページ数」はページ番号入力モーダルを開くボタンとし、履歴画面と操作をそろえる。最下段の「再生キューへ戻る」で通常の全体再生予定順を表示する。自分の曲しか編集できない場合は「追加者を変更」を省略する。

単曲削除は確認画面を挟まない。選択曲名を一覧内に明示してから削除を受け付け、削除後は未選択へ戻すことで連打による別の曲の削除を防ぐ。将来、一括削除を追加する場合は確認を必須とする。

移動成功後は項目IDで選択を維持し、新しい位置へマーカーを移す。ページをまたいだ場合は移動先ページを表示する。手動のページ切り替え・追加者切り替えでは選択を解除する。更新では対象が表示ページに残っている場合だけ選択を維持する。削除後や対象の再生開始後は選択を解除し、隣の曲を自動選択しない。ページ減少時は有効なページへ補正し、空の場合も更新・戻る手段を残す。

編集結果は本人専用の一覧と一緒に更新し、「曲Bを、@追加者の待機曲の先頭に移動しました」のように対象と結果を示す。移動・削除ごとの公開通知は送らない。「次に再生します」とは表示しない。定期更新は行わない。

## 同時操作・保存

動画URLや表示番号ではなく、追加された各項目の一意なIDで対象を特定する。同じ動画の重複追加は別項目として扱う。編集によって追加者・曲情報・自動再生設定・再生履歴は変更しない。削除・並び替えを既存のキュー保存へ反映し、管理再起動後も維持する。

選択・認可・変更の間に対象が再生開始または削除されていた場合は、別の曲へ操作を振り替えず一覧を更新して知らせる。表示から実行までに対象追加者の曲順・件数が変わった場合は、移動を適用せず最新一覧で再操作を求める。他の追加者だけの変化は、この競合の理由にしない。

同一画面の連打・古い世代のボタン・モーダルを二重適用しない。別画面からの操作も、認可した対象と順番が変更時点で一致することを確認する。更新された本文・選択状態・ボタンを一体で扱い、Discord送信中はキューのロックを保持しない。期限切れ・再起動で継続できない編集画面は、新しく開き直すよう案内する。

## 画面の有効期限と保持上限

編集画面は作成から15分で失効し、操作・更新・追加者選択画面への切り替えで期限を延長しない。期限後は編集画面を開き直すよう案内する。

保持上限は1,024画面とする。上限に達した場合は期限切れの画面を先に破棄し、それでも空きがなければ新しい編集画面の作成を断る。有効な既存画面を追い出さない。

## 検証・完了条件

静的な表示サンプルは `mise run ui-preview -- queue-edit-selected queue-edit-11 queue-edit-91 queue-edit-owners` で検証用Webhookへ送信できる。認証情報は既存のGit管理外の `.env.ui-preview` を使う。1〜10番・11〜20番・91〜100番の選択マーカーと追加者選択画面を比較する。操作部品は配置を示すテキストであり、実際のボタン・メニューの描画や動作を検証したことにはしない。

- 各プリセットで本人・他人・DJ等の削除／並び替え、追加forbid、片方だけの許可、VC退出・移動・ロール変更、評価失敗を確認する。
- 移動前後で追加者内の順序だけが変わり、巡回規則と再生中の曲への考慮が維持される。先頭・末尾・同じ位置・範囲外・空一覧も確認する。
- 重複動画、再生開始との競合、他画面の編集、古いボタン、連打、モーダル入力中の変更で別項目を誤操作しない。保存と再起動後の順序・削除結果も確認する。
- 削除後の未選択、ページ番号入力、追加者選択のページ分け、通常キューへの復帰、期限切れ・保持上限を確認する。編集結果が本人だけに表示され、公開通知を増やさないことを確認する。
- Webhookでマーカー、太字リンク、subtext、メンション、長い曲名を比較し、1〜10、11〜20、91〜100番の桁境界を確認する。PC・スマホの表示と実Botの選択・移動・ページ追従は別に検証する。
- 実装時に現行仕様・認可表・helpと対応する検証結果を更新する。未実装・未検証の範囲を対応済みと記載しない。
